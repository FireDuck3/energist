# Етап 4б: рейтинги, скарги, «Перевірена точка» — дизайн

## Мета
Гість може оцінити, чи довіряти господарю й точці, а будь-хто — повідомити про проблему (неправильна адреса, обладнання, несправність, шахрайство). Позначка «Перевірена точка» з'являється лише після справжньої перевірки, не за бажанням господаря.

## Що вже є
- Відгуки: `booking_reviews` лише після `completed` (RLS); публічні відгуки гостей про точку — `list_public_spot_reviews()` (без архівованих точок); рейтинг точки рахує `spotRating(spot)`.
- На сторінці приватної точки — ім'я господаря без рейтингу.
- Публічні станції не мають жодного способу повідомити про несправність.

## Цілі
1. **Рейтинг господаря:** середня оцінка й кількість відгуків по всіх його активних точках — на сторінці точки біля імені господаря («★ 4,8 · 12 відгуків про господаря»). Без відгуків — «Новий господар».
2. **Рейтинг точки:** як зараз; без відгуків — «Нова точка» замість порожніх зірок.
3. **Скарги й повідомлення про проблеми:** одна модель для трьох цілей:
   - приватна точка (причини: неправильна адреса, неправильне обладнання, не працює, небезпечно, шахрайство, інше);
   - публічна станція (неправильна адреса, неправильне обладнання, не працює / закрита, інше);
   - користувач — лише співрозмовник по бронюванню (шахрайство, образи, спам, не з'явився/не надав доступ, інше).
   Кнопки: «Повідомити про проблему» на сторінці приватної точки й у картці/popup публічної станції; «Поскаржитися» в чаті бронювання. Скарга — причина + опис до 1000 символів.
4. **«Перевірена точка»:** позначка ✓ на карті й сторінці точки, лише коли `verified_at` встановлено адміністратором (Етап 5; до того — лише через SQL). Зміна адреси, роз'єму чи потужності господарем знімає позначку автоматично.

## Не цілі
Розгляд скарг і блокування (адмін-панель, Етап 5), публічний рейтинг гостей, відповіді господаря на відгуки, автоматичне приховування точок за скаргами.

## Підходи
1. **Одна таблиця `reports` + RPC `submit_report` з перевірками на сервері; рейтинг господаря рахується з уже публічних відгуків на клієнті (обрано).** Немає нових публічних даних, мінімум SQL.
2. Окремі таблиці для скарг на точки, станції й людей — дублює логіку й ускладнить адмін-панель; відкинуто.
3. Рейтинг господаря як матеріалізоване поле в БД — зайве при поточних обсягах; відкинуто.

## Дизайн
**Міграція `202611180004_trust.sql`:**
- `pilot_spots.verified_at timestamptz` (змінює лише `service_role`; у `update_pilot_spot` — скидання в `null`, якщо змінились `lat`, `lng`, `connector` чи `power_kw`).
- `reports(id uuid, reporter_id uuid default auth.uid(), target_type text check in ('spot','station','user'), target_id text, booking_id uuid null, reason text, details text ≤1000, status text default 'open' check in ('open','resolved','rejected'), created_at, resolved_at, resolution text)`. RLS: автор бачить лише свої; запису напряму немає.
- `submit_report(target_type, target_id, reason, details, booking_id default null) returns uuid` — security definer: активний акаунт; причина з дозволеного списку для типу; ціль існує (точка видима й не архівована; станція активна; користувач — співрозмовник у вказаному бронюванні, не сам автор); не більше 10 скарг на добу від автора; не більше однієї відкритої скарги автора на ту саму ціль (`unique` частковий індекс); на власну точку скаржитися не можна.

**Фронтенд:**
- `js/trust.js` (чисті функції): `REPORT_REASONS` за типом цілі, `hostRating(spots, ownerId) → {avg, count}`, `ratingLabel(avg, count, kind)` («★ 4,8 · 12 відгуків» / «Нова точка» / «Новий господар»), `validateReport({reason, details}, type) → {ok, errors}`.
- `js/views/report.js`: модалка скарги (чипи причин, опис, відправка, помилки, подяка).
- `js/supabase.js`: `submitReport(...)`; `toPilotSpot` додає `verified: Boolean(verified_at)`.
- Сторінка точки: рейтинг господаря, «Нова точка», ✓ «Перевірена точка» з поясненням, кнопка «Повідомити про проблему» (не для власника й не для демо-точок).
- Карта: ✓ у картці перевіреної приватної точки; «Повідомити про проблему» в popup публічної станції.
- Чат: «Поскаржитися на співрозмовника».

**Тести:** `tests/trust.test.js`; SQL — ручний чекліст у README (ліміти, дублікати, скарга на чужого користувача без бронювання → відмова, скидання `verified_at` при зміні адреси).

## Мої рішення
- Рейтинг господаря рахуємо лише з публічних відгуків гостей про його точки (відгуки господаря про гостей не публічні).
- Ліміт 10 скарг на добу й одна відкрита скарга на ціль від одного автора.
- Скаржитися на користувача можна лише в межах спільного бронювання.
- Позначку ставить лише адміністратор; доки немає адмін-панелі — через SQL (`update pilot_spots set verified_at = now() where id = …`).
