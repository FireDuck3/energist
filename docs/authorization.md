# Авторизація учасників

Гілка: `feat/user-authorization`. Backend — Supabase Auth + PostgreSQL.

## Модель

`public.users`: `id`, `first_name`, `last_name`, `email`, `registered_at`, `status` (`active`, `suspended`, `disabled`). Email має унікальний індекс без урахування регістру. Тригер створює учасника атомарно з Auth-користувачем та синхронізує зміну email. Клієнт може читати лише свій запис; змінювати статус може лише адміністратор через довірений backend/SQL.

Хеш пароля зберігає Supabase Auth у `auth.users.encrypted_password`. Він не дублюється у `public.users` і не доступний браузеру. JWT access token і refresh token, оновлення та завершення сесії обслуговує Supabase SDK. Профіль ролі та відображуваного імені залишається в `profiles`.

## Реєстрація й вхід

Форма реєстрації передає ім’я, прізвище, email та пароль. Email нормалізується; пароль реєстрації — 8–128 символів. Старі паролі зберігають сумісність при вході. Перевірка імен виконується і тригером PostgreSQL. Пароль перевіряє та хешує Auth; мінімум 8 символів потрібно також налаштувати на сервері.

`verifyUser()` звертається до `auth.getUser()` і читає актуальний статус з БД. Обмежувальні RLS-політики забороняють неактивному акаунту роботу з профілем та історією незалежно від UI і строку JWT. Це не забороняє саму видачу токена Auth: для повної заборони входу адміністратор також має заблокувати користувача через Supabase Auth Admin.

## Застосування

1. Для нової БД виконати `supabase/schema.sql`; для наявної повторювати його не потрібно.
2. Виконати `supabase/migrations/202611100001_users.sql` один раз у SQL Editor або системою міграцій.
3. Authentication → password policy: мінімум 8 символів. Політика максимуму 128 наразі клієнтська; за потреби суворого серверного максимуму потрібен password verification hook.
4. Зберегти поточний режим Confirm email або увімкнути його з налаштованою поштою. При потребі підтвердження форма показує відповідне повідомлення; після підтвердження користувач входить паролем.
5. Опублікувати клієнт лише після успішної міграції.

Наявним акаунтам без прізвища міграція залишає порожнє прізвище, не вигадуючи персональних даних. Нові акаунти зобов’язані передавати обидва поля. Перед застосуванням перевірити міграцію на тестовому Supabase: дубль email, відсутні імена, вхід/вихід, читання іншого користувача, зміна власного статусу та доступ заблокованого акаунта. Міграція й налаштування живого сервісу автоматично не застосовуються.

## Вхід через Google

На вкладках входу й реєстрації додано «Продовжити з Google». Використовується Supabase OAuth з PKCE; одноразовий код обмінюється через `exchangeCodeForSession`, видаляється з URL, після чого відновлюється попередня внутрішня сторінка. Незавершений профіль просить вибрати роль. Після повернення на картку зарядки користувач повторно натискає «Забронювати»: довільні відкладені JS-дії через перенаправлення не зберігаються.

Налаштування для адміністратора:

1. Застосувати `supabase/migrations/202611100002_google_oauth.sql` після першої міграції users. Вона підтримує Google metadata й відсутнє прізвище; статус ніколи не береться з користувацьких metadata.
2. У Google Cloud / Google Auth Platform створити OAuth client типу Web application. Authorized JavaScript origins: `https://wattway.onrender.com`; для локальної перевірки додати `http://localhost:8420`.
3. Authorized redirect URI Google: `https://yxbpobiipcdazwnshime.supabase.co/auth/v1/callback`.
4. Supabase → Authentication → Sign In / Providers → Google: увімкнути провайдера, внести Client ID та Client Secret. Secret зберігати лише у Supabase, не в репозиторії.
5. Supabase → Authentication → URL Configuration: Site URL `https://wattway.onrender.com`; Redirect URLs: `https://wattway.onrender.com/` і за потреби `http://localhost:8420/`. Для іншого localhost origin потрібен окремий дозволений URL.
6. Налаштувати OAuth consent screen і test users, якщо Google-проєкт у Testing. Перевірити вхід новим і наявним акаунтом, скасування, вихід, повторний вхід та заблокований статус. Користувач проходить Google-вхід сам.

Google-акаунт не має локального пароля: секрети й перевірку особи обслуговують Google та Supabase Auth. Міграцію та налаштування провайдера на живому сервісі ця зміна автоматично не застосовує.

Офіційна документація: https://supabase.com/docs/guides/auth/social-login/auth-google та https://supabase.com/docs/guides/auth/sessions/pkce-flow.
